## 一、网关只看得见一个后端（已改：`106b4e8`）

**现象**：副本扩到 2 个，但请求全部落在其中一个，另一个 CPU 一直是 0。

**原因**：`AspireServiceDiscovery.Load` 拿「服务名」当字典的键，Aspire 注入的
`services__x__http__0` / `services__x__http__1` 会互相覆盖，最后只剩一个地址；
`VivGatewayRouteBuilder` 生成的 cluster 里也只有 `d1` 一个目标，负载均衡选谁都一样。

**改法**：`Load` 改成按末尾索引聚合成列表；`RouteBuilder` 按列表生成 `d1..dn`。
顺手把 `SessionAffinity` 配上（现在 `UseSessionAffinity()` 是空转，cluster 上没有亲和配置）。

**风险**：低。但 WebSocket 升级要单独验一次 —— 同一条连接不能一会儿落 A 一会儿落 B。

**实际改法**：外层仍按服务名收、内层按端点序号收（`SortedDictionary<int, Uri>`），
同一序号上的 http/https 只留 http（同一个副本的 TLS 端口混进 cluster，一半请求会打到加密端口）。
`GatewayService.Uri` 变成 `Uris` 列表，cluster 按列表生成 `d1..dn`。

`SessionAffinity` **没配**，和上面「顺手配上」的判断相反：亲和靠 cookie，
而原生 IM 客户端没有 cookie 罐子；WebSocket 升级是单条长连接，落点在建连那一刻就定了，
不需要逐请求亲和。真要粘性的是 negotiate 那一跳，Kinna 原生端点不走协商。
留给人工验的是「扩到 2 个副本后，WS 长连接是否稳定停在同一个目标上」。

启动时多了一行自检日志：`网关已加载 N 个集群，目标数：cluster-apex=2；...`。
起第二个副本后这里的数字应该跟着变，永远停在 1 就说明多端点又被按服务名合并了。

## 二、限流配额会翻倍（已改：`e162221`）

**现象**：同一个 IP 的限流阈值实际变成了 N 倍。不报错、不告警，只是保护悄悄失效。

**原因**：`Microsoft.AspNetCore.RateLimiting` 的固定窗口计数在进程内存里，每个副本各算各的。

**实际改法**：计数搬到 Redis，一条 Lua 脚本里做完 `INCR` + 首次 `PEXPIRE`
（分两条命令的话，进程在中间崩掉会留下永不过期的键，那个客户端就永久 429）。
键是 `viv:rl:{客户端IP}:{窗口序号}`，不同窗口天然是不同的键。

两个决定值得记下来：

1. **没用框架的 `AddRateLimiter` 策略。** 它的分区工厂是同步签名
   （`Func<TKey, RateLimitLease>`），等不了 Redis，只能在请求线程上阻塞 ——
   在网关这种高并发入口是明摆着的线程池风险。改成自写中间件，
   路由上原来那 4 处 `RateLimiterPolicy` 一并删掉：留着就是两道闸口，
   而第二道恰好是每副本各算一份的本地计数，比不挂更糟。

2. **Redis 不可用时不放行全部，退回本机分区计数。** 直接放行等于「Redis 一抖防刷就没了」，
   比多放几倍请求更糟。代价是这段时间里阈值会随副本数放大；日志里有一条警告，
   只打一次（挂掉期间每个请求打一行会把日志淹掉）。

`QueueLimit` 现在只在兜底路径生效：分布式计数要跨进程排队，代价远大于收益，
正常路径超限直接 429 + `Retry-After`。

**上线前置条件**：网关要有 Redis 连接。配置在 `VivOptions.CacheOption`，
没配时 `IRedisService` 根本不注册，限流就一直停在「每副本各算一份」。
这份配置没有入库（`appsettings.Development.json` 被 .gitignore 忽略），按环境注入。

## 三、同一个人可能拿到两条连接，收到两份消息（已随第四条解决）

**现象**：滚动发布期间、或者客户端网络抖动重连时，同一条消息推两遍；偶尔还会「连上就被断开」。

**原因**：连接表在进程内。A 副本不知道 B 副本上有同一个人的连接。

（组表也在进程内，但这不是问题：每个副本只管给自己手上的连接加组、自己推，
广播事件本来就是每实例一份 fanout。真正造成重复的是「同一端有两条连接」，不是组表。）

**改法**：见下一条 —— 这两条其实是同一件事的两半。

## 四、自动顶号只在本副本生效（已改：`56e0588`）

先把「顶号」说清楚：**新连接进来时，把同一个人的旧连接踢掉**，避免一个人身上挂两条。
原来这段逻辑只在「自己这台机器」的连接表里找旧连接。旧连接在别的机器上就找不到，
于是那个人两条都在 —— 推送时两条都发，用户看到重复消息。

看起来是一行就能改的事，但**直接换方法会踩坑**：

```
现在：本机找旧连接 → 逐条踢（故意跳过自己这条新连接）
想改：让别的机器也踢
错法：调「到处踢」那个方法
```

因为「到处踢」内部是**两步**：先踢本机、再广播给别的机器。它踢本机时不排除自己 ——
新连接已经登记进表了，就会被自己这一脚踢掉，用户看到的是「连上 → 被断 → 重连 → 又被断」。

**所以只要「广播」那一半。** 同一个类里有个私有的 `PublishKickAsync`，它就是只广播、不踢本机，
`RegisterAsync` 直接调它即可，不需要新增接口。接收端会跳过「这条指令是我自己发的」。

### 三个坑，改的时候挨个踩过

1. **指令必须带 `AppId`。** 留 0 会被订阅端当成「踢这个人所有端」，
   把他在别的设备上的连接一起断掉，`SingleConnectionPerApp` 的语义就废了。

2. **判定要带连接 Id，不能只比时间。** 两条连接几乎同时到达 A、B 时，
   时钟给出的时间可能完全相同：用 `<=` 两边都踢（互相踢掉、来回抖动），
   用 `<` 两边都不踢（留下两条）。改成 `(建立时间, 连接 Id)` 全序之后，
   任意两条之间恰有一个「更旧」，收敛结果永远是「留下一条」。

3. **「建立时间」得单独存。** 连接表里原来只有「最后心跳时间」，心跳一直在刷新它，
   拿它判新旧永远判不出来。现在 `Add` 返回表里真正记下的那个时间，
   广播用的就是这个值 —— 各自取一次时钟的话，两个副本可能判不出谁更旧。

### 原来这条的二阶问题里，有一半是错的

原文说「两个副本的 `InstanceId` 配成一样 → 跨副本踢人静默失效」，**不成立**：
踢人用的 `InstanceId` 是 `{机器名}-{随机guid}` 的进程级静态值，根本配不了，也撞不上。

真正可配的是 `NanaOptions.InstanceId`，它是**广播队列名**
（`{Event}Queue.{Service}.{InstanceId}`）的最后一段。配重了确实会静默出问题，
但那是「两个副本抢同一条 fanout 队列、消息被其中一个抢走」，影响的是消息投递，不是踢人。
它默认从 `POD_NAME` / `HOSTNAME` / `{机器名}-{进程Id}` 推导，正常部署不会撞。

### 还剩一个已知窗口

同一个副本上，同一个客户端的两条连接几乎同时登记时，两次快照可能互相看不见，
两条都会留下（靠租约过期回收）。这个窗口原来就有，而且广播救不了它 ——
本副本会按 `Origin` 跳过自己发的那条。窗口是微秒级，不值得为它加锁。

### 另一条路（更干净，但改动更大）

不做广播，改用 Redis 记「这个客户端当前是哪条连接」。旧副本在心跳时发现自己已经不是当前那条，
就按现有「心跳返回不存活 → 客户端重连」的路自然退出。没有广播窗口，也不怕抖动。
代价是每次心跳多一次 Redis 读（心跳本来就在读在线态）。这次没走这条，
因为广播这条路能复用现成的 `IKinnaKickBus`，改动面小得多。

## 还剩一件旧的：消息序号会撞号（已改：`e162221`）

**现象**：同一个会话里两条消息序号一样。客户端排序会乱，或者把后一条当成重复丢掉。

**原因**：`NextSeqAsync` 是「把该会话的消息全查回来取最大值 +1」。
两个请求同时进来，两边都读到 10，都写 11 —— 包事务解决不了，它是读-改-写，不是写。
`OtMessage` 上也没有 `(ConversationId, Seq)` 唯一约束，数据库不会拦。
顺带还有个跟扩容无关的问题：长会话每发一条消息都要把全部历史读回内存。

**实际改法**：`OtConversation` 加 `NextSeq` 列，取号变成一条语句：

```sql
UPDATE OtConversation
SET NextSeq = CASE WHEN NextSeq = 0
    THEN (SELECT MAX(Seq) + 1 FROM OtMessage WHERE ConversationId = @Id)  -- 首次对齐
    ELSE NextSeq + 1 END                                                  -- 正常自增
OUTPUT INSERTED.NextSeq          -- PostgreSQL 是 RETURNING NextSeq
WHERE Id = @Id
```

`UPDATE` 会拿到会话行的排他锁，两个副本同时取号在这里排队，拿到的一定不同。
`CASE` 让「首次对齐」和「自增」在同一条语句里完成 —— 分开写的话两者之间有窗口。

`NextSeq = 0` 当作「还没初始化过」的哨兵，所以**老库加列后不需要迁移脚本**：
第一次取号时按 `MAX(Seq)` 自动补上，之后一直自增。

另外两处必须一起改：

- **助手消息不再用「用户消息 seq + 1」。** 模型跑一轮的期间，同一个会话完全可能插进
  别的消息（并发的另一个请求、工具回调里另起一轮），`+1` 会和那条撞上。
  现在用户消息和助手消息各取一次号，序号会有空洞 —— 排序只看大小，不看连续性。
- **带写的标量查询要走写连接。** 新增 `FindScalarWriteAsync`：原来的 `FindScalarAsync`
  固定走读连接，而读连接可能是只读从库（写语句直接失败），主从有延迟时还会读到旧水位。

**部署注意**：加列不在服务启动时做，要跑一次 `viv init`（内部是 `SyncTableAsync`）。
没跑的话取号会报「列不存在」，表现是发消息全失败 —— 报错信息里带原始 SQL，能看出来。

**没做的**：`(ConversationId, Seq)` 唯一约束。序号现在由 `NextSeq` 单点发放，不会撞；
加唯一索引的价值是防「绕过取号手工插数据」，但存量库里已经可能有重复（老代码就会撞），
建索引会失败。要加的话先查重、清完再加。

**验证**：真库测试在 `AgentStoreSequenceTests`，两种方言各跑一遍
（PostgreSQL 走 `RETURNING` 分支、SQL Server 走 `OUTPUT INSERTED` 分支），
覆盖并发取号不重号（30 并发恰好拿到 1..30）、老会话首次取号从 `MAX(Seq)` 之后开始、
会话不存在时抛异常。需要 `VIV_CONTAINER_TESTS=1` 且本机 Docker 可用，否则自动跳过。
已实际跑通：6 条全绿。

**顺带发现一个跟扩容无关、但影响新环境部署的问题**：
`SyncTableAsync` 的第一步是 EF 的 `EnsureCreatedAsync`，它把 `long` 主键建成
`IDENTITY(1,1)`；而框架插入前会塞一个雪花 Id（`SetIdentityAndTenant`），
显式值写 identity 列会直接报 `IDENTITY_INSERT is OFF`，**整表插不进数据**。

Postgres 上建的是 `GENERATED BY DEFAULT AS IDENTITY`，允许显式值，所以一直没暴露。
SQL Server 只有「空库首次建表」会踩 —— 库里已有表时 `EnsureCreated` 什么都不做，
后续由 `SchemaSynchronizer` 补表，而它的 DDL 不带 IDENTITY（判据是属性上有
`[DatabaseGenerated]`，`EntityBase.Id` 只有 `[Key]`）。所以存量库正常、全新部署会挂。

测试里对 SQL Server 用 `IsAutoSetDefaultValue(false)` 绕过：那一组验证的是取号语句，
不是发号策略。**这个 Id 策略冲突本身没有修**，要修的话得让两边对齐
（`[DatabaseGenerated(DatabaseGeneratedOption.None)]` + 同步器按 option 值判定），
属于部署链路的独立问题，没有并进这次改动。
