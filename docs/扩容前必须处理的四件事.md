# 扩容前必须处理的四件事

> 写这份的时间点：单个实例跑得好好的，下面这些问题一条都不会出现。
> 但只要起第二个副本（HPA 或多副本），它们会**同时**冒出来，而且表现为「用户能看见的错」，不是日志里的告警。
> 顺序按「改的代价从低到高、卡脖子的程度从高到低」排。

## 一、网关只看得见一个后端（最卡脖子，必须先做）

**现象**：副本扩到 2 个，但请求全部落在其中一个，另一个 CPU 一直是 0。

**原因**：`AspireServiceDiscovery.Load` 拿「服务名」当字典的键，Aspire 注入的
`services__x__http__0` / `services__x__http__1` 会互相覆盖，最后只剩一个地址；
`VivGatewayRouteBuilder` 生成的 cluster 里也只有 `d1` 一个目标，负载均衡选谁都一样。

**改法**：`Load` 改成按末尾索引聚合成列表；`RouteBuilder` 按列表生成 `d1..dn`。
顺手把 `SessionAffinity` 配上（现在 `UseSessionAffinity()` 是空转，cluster 上没有亲和配置）。

**风险**：低。但 WebSocket 升级要单独验一次 —— 同一条连接不能一会儿落 A 一会儿落 B。

---

## 二、限流配额会翻倍

**现象**：同一个 IP 的限流阈值实际变成了 N 倍。

**原因**：`Microsoft.AspNetCore.RateLimiting` 的固定窗口计数在进程内存里，每个副本各算各的。

**改法**：计数外置到 Redis（自管窗口 + `INCR` / `EXPIRE`，替掉 `GetFixedWindowLimiter`）。

**说明**：网关只有一份时这**不是** bug，所以别急着改 —— 它是扩容的连带项，跟着第一条一起做最省事。

---

## 三、同一个人可能拿到两条连接，收到两份消息

**现象**：滚动发布期间、或者客户端网络抖动重连时，同一条消息推两遍；偶尔还会「连上就被断开」。

**原因**：连接表、组表都在进程内。A 副本不知道 B 副本上有同一个人的连接。

**改法**：见下一条（这就是它的半成品）。

## 四、自动顶号只在本副本生效（最容易改错的一条）

先把「顶号」说清楚：**新连接进来时，把同一个人的旧连接踢掉**，避免一个人身上挂两条。
现在这段逻辑只在「自己这台机器」的连接表里找旧连接。旧连接在别的机器上就找不到，
于是那个人两条都在 —— 推送时两条都发，用户看到重复消息。

看起来是一行就能改的事，但**直接换方法会踩坑**：

```
现在：本机找旧连接 → 逐条踢（故意跳过自己这条新连接）
想改：让别的机器也踢
错法：调「到处踢」那个方法
```

因为「到处踢」内部是**两步**：先踢本机、再广播给别的机器。它踢本机时不排除自己 ——
如果新连接已经登记进表了，就被自己这一脚踢掉。用户那边看到的是「连上 → 被断 → 重连 → 又被断」。

而且本机那一步是**多余**的：现有代码已经精确踢过旧连接，还特意跳过了自己。

**所以只要「广播」那一半。** 同一个类里有个私有的 `PublishKickAsync`，它就是只广播、不踢本机，
`RegisterAsync` 直接调它即可，不需要新增任何接口。

**为什么这样是安全的**：接收端会跳过「这条指令是我自己发的」，所以本副本不会把同一件事做两遍。

### 改之前要知道的两个二阶问题

1. **两个副本的 `InstanceId` 配成一样 → 跨副本踢人静默失效。**
   跳过「自己发的」是靠比对 `InstanceId`。配重了，所有广播都会被所有副本当成自己的而跳过。
   （这个值同时还是每实例广播队列名的最后一段，配错的影响不止踢人。）改完要加一条启动自检日志。

2. **两条连接几乎同时到 A、B → 互相踢，来回抖动。**
   根治要给连接记「建立时间」，只让更旧的被踢；现在连接表里只有「最后心跳时间」，得补一个字段。

### 另一条路（更干净，但改动更大）

不做广播，改用 Redis 记「这个客户端当前是哪条连接」。旧副本在心跳时发现自己已经不是当前那条，
就按现有「心跳返回不存活 → 客户端重连」的路自然退出。没有广播窗口，也不怕抖动。
代价是每次心跳多一次 Redis 读（心跳本来就在读在线态）。

## 还剩一件旧的

**消息序号会撞号**：`NextSeqAsync` 是「把该会话的消息全查回来取最大值 +1」，`OtMessage` 上也没有

包事务解决不了（它是读-改-写，不是写）。要加唯一约束 + 改取号方式，单独做。
